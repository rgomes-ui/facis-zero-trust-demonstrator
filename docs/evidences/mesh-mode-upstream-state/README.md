# Mesh mode: the upstream state behind the decision

`upstream-state.md` and `environment.json` are the evidence behind
[ADR-0009](../../adr/0009-service-mesh-mode-istio-sidecar-with-cilium.md), the record that moves the
service mesh from Istio ambient to Istio sidecar mode. They are written by
`scripts/mesh-mode/check-upstream-state.sh` and never by hand: the files in the repository are the
output of the last run, on the commit and host that `environment.json` names.

## What the record is

The decisive question of the WP05 gate, whether the mesh can use SPIRE-issued identities under
ambient mode, is answered by the upstream itself rather than on a cluster. The record fetches and
dates the facts the decision rests on:

- the latest Istio release and the entry under *What is not supported* in Istio's sidecar-to-ambient
  migration guide that names SPIRE as the certificate provider, with the fetched excerpt;
- the state of the Istio tracking issue for SPIRE under ambient (istio/istio#42339) and of the
  ztunnel pull requests for the Delegated Identity API (#1676), the SPIFFE Broker API client (#1936)
  and the per-workload cache groundwork (#2067);
- the latest SPIRE release and whether its agent documentation still places the Broker API under
  the `experimental` configuration block.

## Why it is documentary

Installing SPIRE under ambient to show that the mesh ignores it would prove what Istio states in
writing. What the project needs is a dated, versioned statement that can be regenerated, not a web
citation in prose; the record is that statement. The accepted risk, that this is the project's one
gate verdict without a cluster run, is written in the decision record, and an executed probe on
kind (community Istio in ambient over the chained Cilium, showing that ztunnel's certificate source
is istiod and that the ztunnel chart has no SPIRE option) is specified as a conditional task to add
if the review of the decision record asks for executed evidence.

## How to re-run it

```bash
scripts/mesh-mode/check-upstream-state.sh
```

Needs `curl`, `jq`, `python3` and `git`; uses `gh` for the GitHub API when it is installed and
logged in, `curl` otherwise. Run it on a clean tree and commit the two files it rewrites; the
commit and the dirty flag it records are the proof that the record matches the tree. The script
refuses to run under CI (`CI` set), because this evidence is regenerated by an operator and
committed, never written by a pipeline.

## It is the reopen check

ADR-0009 is reopened only when both of the following hold in released versions: a community Istio
release whose ztunnel obtains workload certificates from the SPIRE agent through the SPIFFE Broker
API, documented as supported in ambient mode; and a SPIRE release in which the Broker API is a
stable agent feature outside the `experimental` block. The script checks the premises of both:

| Exit | Meaning |
|---|---|
| `0` | every premise holds: the statement is in the guide, no ztunnel client has merged, the Broker API is experimental |
| `1` | a premise moved; the record names it. One condition alone does not reopen the decision, so the next step is to read the record and judge the double condition |
| `2` | a source was unreachable, answered with an HTTP error status, or answered with a document that lacks the expected shape (the migration guide's title, the SPIRE agent document's reference heading); the record says so, names the expected shape, and claims nothing about that source |
| `3` | refused under CI |

The failure paths are tested by `scripts/mesh-mode/check-upstream-state-test.sh` against local
stand-ins answering 404, 500 and the wrong document; CI runs it with the record in a temporary
directory and checks that this folder is unchanged.

The decision record names when the check is made: at every Istio minor upgrade, beside the CNI
chaining check that runs after every Cilium upgrade.
